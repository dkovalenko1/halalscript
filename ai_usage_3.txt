2. WHAT THE AI PRODUCED, PART BY PART
-------------------------------------

Reading the task (prompt 1). The AI summarised the stage: the three tasks, the
grading, the AI disclosure rule, the defence and the submission steps. It
pointed out that the draft pull request due on 30 October had not been opened
and that the deadline was the same day. It recommended loops as the feature,
because the stage 1 grammar had reserved ma_dama for a while loop and because
an interactive program needs a loop to read a list of values.

Task 3, the first program (prompt 2). The AI created the branch stage3 from
stage2 and wrote programs/zakat_ledger.txt: a Purse diwan with the member dua
add, a ma_dama loop that reads amounts until 0, the dua share that divides by
repeated subtraction (the language has no '/'), and the pipe
purse.total |> zakatable |> share(1, 40). To make it run, it added to the
compiler, before I asked for the rest of the features: the ma_dama loop, the
|> pipe, and the comparisons < <= > >=, which the language did not have. It
explained that a loop with only == and != can only stop at one exact value.
It recorded two sessions (zakat_ledger.due and zakat_ledger.exempt), extended
check.py to run every session of every program in programs/, and built the
program into a native binary with llc and clang on the Linux machine. Taken as
generated.

Task 1, loops (prompt 3). The AI added kull dirham i := a ila b, an inclusive
range whose bounds are computed once, and kafa, which leaves the innermost
loop. It chose the keywords so that their Arabic meaning matches the role, as
the stage 1 design rules require (kull "each", ila "up to", kafa "enough"),
and checked that no existing program used them as names. The counter cannot
be assigned and lives only in the loop; the loop stops before adding 1 at the
last value, so a range up to the largest dirham does not overflow. It added 3
valid and 5 invalid loop tests, each aimed at one way the lowering could go
wrong (kafa leaving only the inner loop, the range edges, ameen inside a loop,
kafa outside a loop, the counter assigned or used after the loop). Taken as
generated.

Task 2, the optimizer (prompt 3). The AI wrote src/optimizer.py and the
--optimize flag. Unused duas are found by walking the calls from the top
level, so duas that only call each other are removed too. Unused variables are
counted per declaration through the links the semantic pass already stored.
Inlining replaces a global dua called once with its body: parameters become
declarations named f.<param>, locals are renamed f.<name>, and the answer goes
into f.ameen; a '.' cannot appear in a source name and ameen is reserved, so
nothing collides. It leaves alone member duas, recursive duas, bodies with an
ameen inside a block, calls in a ma_dama condition, and calls that come after
another effect in the same statement. It added 7 programs to tests/opt and a
--optimize mode to check.py that runs the whole suite with the flag.

While testing the optimizer, the AI found and fixed two of its own mistakes:
the answer variable was first named f.result, which collided with a local
named result in a test; and one test claimed that a call would not be inlined
when it rightly was. To check that the tests catch real faults, it broke each
rule of the optimizer on purpose, one at a time, and confirmed that a test
failed. One broken rule was not caught (a dua reached only through another
dua), so it added that case to a test.

Pipes (prompt 4). The AI added the pipe tests, 3 valid and 5 invalid: the
arguments of a stage, precedence, widening between stages, the order in which
stages run, an object flowing through a pipe, a stage inside a member dua, and
the errors that name the stage that does not fit. It also improved two error
messages so that they name the stage: a chain such as c.add used as a stage,
and an unknown dua.

README and grammar (prompts 3 and 4). grammar.ebnf has the rules for ma_dama,
kull, kafa, the comparisons and the pipe. The README has the rules and two
example programs for loops and for pipes, the IR excerpt of a kull loop and of
a pipe with an explanation of each part, the optimizer's rules with the shapes
it inlines and leaves alone, the IR before and after inlining one dua, the
program's description with the llc and clang commands, and the new test
suites. Every example program in the README was compiled and run.

Comparison with the course (prompt 4). The AI compared the new features with
practices 5, 8 and 9, my languages-and-compilers-design repository and the
stage 1 DESIGN.md. It found one violation: the optimizer treated + - * as free
of effects, but DESIGN.md makes overflow (riba) halt the program at runtime,
so removing an unused overflowing value changed the output, against Practice
9's rule "when in doubt, keep". It fixed this: a value with + - * now stays,
except in a wallahi declaration, which the compiler already computed and
checked. A new test checks that the unused overflowing value still halts the
program with --optimize. The other differences from Practice 9 are on the safe
side and are kept: unused member duas are removed too, and duas that call only
each other are removed, which counting could not do.
