2. WHAT THE AI PRODUCED, PART BY PART
-------------------------------------

Reading the task. The AI opened the Moodle calendar, found the assignment due
on 27 October, downloaded w07-project-stage2.pdf and summarised its four
tasks, the grading and the submission steps.

Task 1, language design. The AI proposed the syntax after reading practices 6
and 7, the Practice 7 grammar of my course repository, and the stage 1
DESIGN.md: `dua` for functions, `diwan` for structures, fields declared with
`bismillah` or `inshallah`, `ameen` as the return inside a dua, `Point(3, 4)`
to create an object, `sual()` to read and `bayan(...)` to print. It avoided
words tied to acts of worship (iqra, adhan, khutba) for read and print, as the
stage 1 design rules require. It also wrote the grammar.ebnf changes and the
README sections. Taken as proposed, except for the decisions in section 3.

Task 2, front end. src/lexer.py gained the four keywords, ',' and '.', and
string literals checked as UTF-8. src/parser.py gained one method per new rule
(diwan, field, dua, postfix chain, arguments, bayan) and the fixed program
order. src/ast_nodes.py gained the new node classes and their --ast labels.
Taken as generated.

Task 3, semantic analysis and code generation. src/semantic.py is new: the
symbol tables for variables, duas and diwans, every stage 1 rule from
DESIGN.md (which stage 1 had only designed), and the stage 2 rules, including
the mutation fixed point. src/codegen.py is new: the module through llvmlite's
IRBuilder, with runtime overflow checks through the llvm.s*.with.overflow
intrinsics. Both follow the structure of the SemanticChecker and CodeGen
classes of my languages-and-compilers-design repository (practices 6 and 7).
compiler.py now writes output.ll. Taken as generated.

Task 4, tests. 17 new valid programs, each run end to end, and 61 new invalid
programs, plus check.py rewritten to compile, run under lli with NAME.in as
input, and compare the output. The AI recorded the outputs and error lines by
running the compiler, then read each one and checked it against the program
before keeping it. Two stage 1 files changed: tests/ok/spacing_tight.txt used
an undeclared name, which the new semantic pass rightly rejects, so a
declaration was added; tests/err/decl_missing_type.expected now also lists "or
a diwan" among the types. When I asked for an audit of the tests (prompt 6),
the AI listed what each one covers, found three invalid programs that ran the
same code path as another test, and found gaps: the three-way name collision
in a member dua, a local named like a field, duplicate names, and --ast dumps
of chains and strings. It removed the three overlapping programs and added
five programs and two .ast files for the gaps.

Extra. examples/treasury.halal, a stage 2 example program.

Setup steps (prompt 8). The README's build steps named Homebrew paths; the AI
rewrote them for any platform (the LLVM tools on PATH, commands inside an
activated virtual environment) and removed the Homebrew fallback from
check.py, then ran the new steps as written in a fresh copy of the repository.

VS Code extension (optional, prompts 9 and 10). The AI listed what the stage 1
extension lacked, and on my request implemented all of it: the bundled
compiler now includes the semantic pass, so semantic errors are underlined
live; the TextMate grammar covers diwans, duas, parameters, calls, member calls,
field chains, strings, sual and bayan; the keyword table has rulings for dua,
diwan, sual and bayan; new snippets; a symbol scanner (src/symbols.ts) gives
hovers with dua signatures, diwan fields and fields reached through a chain,
and completion of only the fields and member duas after "chain."; a command
runs the program under lli in a terminal (runner/run_program.py), only in a
trusted workspace, with a new halalscript.lliPath setting. It added a grammar
test for the new scopes, nine integration tests and two fixtures, and three new
screenshot scenes. Taken as generated.

Screenshots (prompt 10). The session had no computer-use tool, so the AI took
the screenshots with the extension's own screenshot script, which drives a
downloaded VS Code and captures the screen. It then looked at each of the nine
images; one hover was cut off by VS Code's maximum hover height, so it shortened
that keyword's example and took the screenshots again.

Trying the extension myself (prompts 11 to 13). My VS Code still ran the
installed 0.1.0 extension, whose stage 1 compiler has no '.' token; the AI
installed the 0.2.0 package. The empty terminal was the program waiting for
its two sual() numbers without saying so; the AI made the runner announce the
program and, when it calls sual(), ask for the input before it waits.


3. WHAT I DECIDED OR CHANGED (relative to the AI's proposals)
-------------------------------------------------------------

- Fatwas print as `halal` and `haram`, not `true` and `false`, and the README
  says in a short note that the task asked for true and false.
- What a dua body sees follows my course repository: no top-level variables at
  all. The AI had proposed that a dua could see the top-level `wallahi`
  constants; it checked my practice repository, found that a function there
  never sees top-level names, and dropped the idea.
- Objects are created as `Point(...)`. The AI had also offered `{3, 4}`.
- The README keeps the voice it had in stage 1.
- The stage only asks the README to state what happens when a parameter, a
  field and a global share a name (prompt 5); globals do not have to be
  visible, so the rule stays as it is, with a test for that exact case.
- Every test must cover a real concern: overlapping tests were removed rather
  than kept for the count (prompts 6 and 7).
- The setup steps must not depend on one platform (prompt 8).
- The extension gets every proposed feature, including the optional ones:
  completion after '.', the run command and new screenshots (prompt 10).
